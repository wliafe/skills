# 团队交接与异步调度

主会话（`lead`）的职责到「把任务边界写清楚、挂到任务板并交给合适的队友」为止。交出任务后立即用简短回执结束当前轮次，把对话控制权还给用户，让用户可以连续安排多个并行任务；队友的结果由完成通知异步带回，不由主会话阻塞守候。

## 为什么主会话不阻塞等待

- 队友在各自独立的上下文中异步运行。如果主会话调用 `wait_agent` 死等或反复轮询状态，不仅会锁死用户输入、无法连续派单，还会让两个层级同时消耗上下文却产生重复输出。
- 主会话交接完任务后给出一句简短回执（说明交给谁、任务号及是否排队）即可结束本轮；等后台队友完成时，系统通知会自动唤醒空闲的主会话（或在主会话忙碌时排队），再由主会话汇总结果并推进下一棒。

## 会话内复用优先与谨慎新建

禁止动辄为每个小步骤都无脑新开一次性队友，也不要把不相关的工作强塞进同一个队友上下文里造成污染。派单遵循**「复用优先、谨慎新建、按需多实例」**：

1. **优先复用（命中上下文，减少重复交代）**
   - 当会话中已有 `inactive` 队友，且其先前建立的上下文与新任务高度相关（例如同一代码模块、同一批文档或连续迭代的同一调研主题）时，优先用 `send_message` 增量续派。
   - 复用时无需重抄背景，只需增量说明「变更点、新任务编号、本次边界与交付项」，既省 Token 又能延续它已经摸清的细节。
2. **谨慎新建（仅在必要时实例化）**
   只在以下情形才新建子智能体：
   - **缺口**：当前会话还没有匹配该类工作或工具链上下文的队友；
   - **隔离**：已有队友的工作域与新任务完全无关，混用会引入无关历史噪音；
   - **并行**：任务有独立且适合并行的部分，并行能明显节省时间或隔离上下文，且读写边界与资源允许；
   - **换新**：已有队友经历过多轮重任务、上下文明显膨胀或任务方向发生根本转向，需要全新上下文干净接班。
3. **同模板可多实例**
   - 同一个会话里可以从同一套模板实例化多个队友，按职责或作用域区分命名（例如 `investigator-code` 与 `investigator-docs`，或 `executor-backend` 与 `executor-tests`），避免所有同类型活挤在同一个实例上串行卡顿。

## 派单前检查与三路调度流程

### 派前两步检查

1. **查任务板（`team_task_list`）**：确认是否已有相同或前置任务正在进行或待认领，避免重复建单；拆单时把需要先后顺序的任务用 `blocked_by` 串起来，把可能改文件的任务显式标上 `write_scopes`。
2. **查队友状态（`list_agents`）**：看清当前会话已有队友的命名、职责边界以及当前状态（未创建 / `inactive` 空闲 / `running` 执行中）。

### 按状态三路分流

#### 路径 A：需要新建队友（使用通用模板 `subagent`）
1. 用 `team_task_create` 创建任务，写清目标、工作路径、允许修改与明确禁止修改的范围、验收标准和需要带回的证据。
2. 判断任务性质属于**只读调查**还是**落地执行**，从下方模板复制提示词并填入具体参数，调用 `subagent` 创建具名队友（默认用 `subagent` 保持独立上下文；仅当任务强依赖主会话刚刚讨论完且未落盘的推理过程时，才考虑 `subagent_fork`）。
3. 向用户给出简短回执后立即结束本轮。

#### 路径 B：目标队友为 `inactive`（增量唤醒复用）
1. 用 `team_task_create` 创建任务，并用 `team_task_update`（`action: "reassign"`）直接把 `owner` 指派给该队友，省去对方盲查任务板的开销。
2. 调用 `send_message` 发送增量续派指令，保持精炼，只写三项：
   - **口径变更 / 纠偏**（如推翻前序某条结论或调整约束，放在第一句写明；无变更则省略）；
   - **本次任务与边界**（任务 ID、具体要做的动作、明确不改的边界）；
   - **交付与核验要求**（需要返回哪些核实后的结果、路径或检查状态）。
3. 向用户给出简短回执后立即结束本轮。

#### 路径 C：目标队友正在 `running`（防插话踩踏）
同一队友同一时刻只能执行一个激活任务；对 `running` 状态的队友发 `send_message` 会触发中途插话（Steer），打断或扭曲它正在做的工作。因此默认采取依赖排队：

- **默认：任务板依赖排队（不发 `send_message`）**
  1. 用 `team_task_create` 创建新任务 B，将 `blocked_by` 设为该队友正在执行的任务 A 的 ID，并用 `team_task_update`（`action: "reassign"`）把 `owner` 提前指派给该队友。
  2. **此时不调用 `send_message`**，向用户说明「队友正忙于任务 A，任务 B 已挂在任务板排队，前置任务完成后由主会话续派」，立即结束本轮。
  3. 当任务 A 的完成通知返回时，主会话先向用户汇报 A 的结果，再紧接着执行「异步续派检查」唤醒已回到 `inactive` 的该队友处理 B。
- **例外：旁路并行实例**
  - 若并行有明确收益或用户要求同时推进，且读写目标与运行资源可以隔离，可复用其他空闲队友或按路径 A 新建同模板实例。

## 两个通用可复制模板

新建队友时，按任务性质二选一复制下方模板，替换尖括号占位符即可。将任务编号、必要背景、可读写范围和验收标准写入派单。本地工作区要求为任务单独建目录时，在任务目录内处理并存放临时产物。

### 模板一：调查者（只读调研 / 查证 / 分析）

适用于代码走读、文档检索、日志排查、方案对比、风险评估等**不改目标代码与正式产出**的工作。把搜索噪音和原始长输出挡在队友内部，只把核实后的结论与出处交回主会话。

```text
你是团队中的调查专员（命名：<例如 investigator-1 / investigator-code>），负责只读核查与结构化分析。

【任务编号与工作流】
- 你的任务 ID：<task-id>
- 请先调用 team_task_get 读取 <task-id> 的完整要求与范围。就绪且尚未认领时，用 team_task_update(action="claim", expected_revision=<最新 revision>) 认领。若任务已指派给你且处于 in_progress，直接执行。前置依赖未完成时等待续派。验收通过后读取最新 revision，再用 team_task_update(action="complete", expected_revision=<最新 revision>) 结项。

【本次调查目标与边界】
- 调查范围：<目标仓库/目录/文档/链接/问题范围>
- 重点核实的问题：<具体需要核实的问题或对比维度>
- 只读护栏：严格保持只读，不得修改业务代码、配置文件、外部仓库或正式文档（除非任务明确指定向临时目录输出调研报告文件）。

【二级委派纪律（仅在确需并发筛选时使用）】
- 如当前运行环境允许且面对多目录/多数据源高噪检索，可适度派生临时子智能体协助筛选，但需根据当前运行时并发配额保持克制，不与主线抢占过多名额；子智能体不得认领主任务板任务。
- 一旦派生了子智能体，必须在你结束本轮前自己调用 wait_agent 等齐所有子智能体并汇总结果，禁止把未等齐的后台分支留给 lead。

【交付要求与结项纪律】
- 将冗长的原始搜索片段与试错过程留在自己上下文内，只汇报核实后的结论、精确文件路径与行号（或可验证出处）、关键数值及未核实/不确定边界。
- 结项前严禁调用 send_message 给 lead（最后一次主动发消息会导致系统完成通知省略你的最终回复正文）；直接在本轮最终回复输出完整报告即可。
```

### 模板二：执行者（实现 / 修改 / 验证）

适用于代码开发、配置修改、脚本编写、文档撰写、本地测试与构建验证等**会产生文件或状态变更**的工作。强调写范围护栏与实测验证，防止并发改写互相覆盖。

```text
你是团队中的执行工程师（命名：<例如 executor-1 / executor-api>），负责在限定写范围内完成修改并验证结果。

【任务编号与工作流】
- 你的任务 ID：<task-id>
- 请先调用 team_task_get 读取 <task-id> 的完整要求、写范围（write_scopes）与前置依赖。就绪且尚未认领时，用 team_task_update(action="claim", expected_revision=<最新 revision>) 认领。若任务已指派给你且处于 in_progress，直接执行。前置依赖未完成时等待续派。验收通过后读取最新 revision，再用 team_task_update(action="complete", expected_revision=<最新 revision>) 结项。

【本次执行目标与写范围护栏】
- 交付目标：<具体要实现的功能/修改的文件/产出的结果>
- 允许写范围（write_scopes）：<明确列出允许创建或修改的目录/文件前缀>
- 禁止事项：<明确不可触碰的目录、配置、分支、外部环境或禁跑操作>
- 如实际工作必须修改写范围之外的文件，不要擅自越界改动（以免与并行队友发生写冲突），请立即停下并在回复中说明原因由 lead 协调。

【验证与二级委派纪律】
- 完成后必须运行与改动匹配的检查或测试（如语法检查、单测、构建或核心验证），在结果中如实区分「已执行通过的检查」与「未运行/受限的检查」。
- 如当前运行环境允许，可适度派生临时子智能体辅助并行检查，但需遵循运行时并发限制克制派生；一旦派生，必须在结束前自行 wait_agent 等齐并整合，不得让子智能体认领主任务板任务。

【交付要求与结项纪律】
- 最终回复必须清晰列出：1) 修改或新增的文件列表（带精确路径）；2) 执行的验证命令与真实检查结果；3) 遗留问题或风险提示。
- 结项前严禁调用 send_message 给 lead（否则系统完成通知会省略你的最终正文）；请直接将完整结果作为本轮最终回复输出。
```

## 任务板状态、依赖、写范围护栏与异步续派

1. **任务状态与依赖流转**
   - 任何任务在团队内遵循统一闭环：`team_task_create`（设好 `write_scopes` 与 `blocked_by`）→ 队友 `team_task_get` 核对最新版本 → 认领或确认已指派的执行状态 → 执行 → `complete`。状态更新使用最新的 `expected_revision`。
   - 存在先后因果、前后依赖同一份产出物、或无法完全切分写入目录的任务，必须用 `blocked_by` 显式串行，不能靠口头约定并行。
2. **写范围护栏（Advisory Scope）**
   - `write_scopes` 是协作边界声明而不是文件系统硬锁：同时有多个执行者并行时，按工作区相对路径登记写范围，并核对其他写入目标和共享资源，例如远程目录、页面或设备。冲突任务用依赖串行。
   - 若执行过程中发现必须跨出自身 `write_scopes`，执行者应停下汇报由主会话重新划分或串行化，避免工具或脚本在无冲突检测的情况下覆盖其他成员的编辑。
3. **异步续派闭环（收到完成通知后的标准动作）**
   - 主会话在收到任一队友的完成通知后：
     1. 先核查结果是否满足任务验收标准，并向用户呈现结论；
     2. 顺手调用 `team_task_list` 检查任务板：如果有 `owner` 指向当前已恢复 `inactive` 的队友、且其 `blocked_by` 前置任务已经全部 `completed` 的任务，选择一项调用 `send_message` 唤醒队友。已就绪的无主任务按派单流程分配。若前置任务受阻，报告原因并保留依赖。任务板状态本身不会启动空闲队友。
4. **星型通信与正文防丢失**
   - 同级队友之间、子层临时代理与主会话之间**不直接互相发消息**。需要「调查者结论 → 执行者落地」或跨成员接力时，一律先回到主会话核对并征求用户必要确认后，再由主会话派给下一棒。
   - 所有子智能体（无论一级还是二级）完成工作时均**直接结束轮次并输出完整正文**，禁止在结束前调 `send_message` 给父级，避免运行时的完成通知吞掉最终正文。
