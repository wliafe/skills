# 个人编码习惯

## 高内聚、低耦合

把围绕同一职责、通常一起变化的逻辑放在一起。让项目和模型之间可复用的逻辑通过清楚的输入、输出与外部协作，减少对调用方内部状态和实现细节的依赖。把项目路径、模型默认参数和具体配置的读取放在调用方或适配层。

## 按职责决定是否拆函数

一个函数承担一项完整、连贯的职责时，可以写得长一些。用准确的局部变量名和自然分段让流程从上往下读得通。一次性的简单逻辑就放在使用处，尤其是拆出去只会增加一次跳转时。

当一段逻辑确实有独立职责、需要复用，或提取后能明显简化主流程时，再考虑拆分。提取后应能给它起一个表达职责的名字，并在调用处看清依赖和结果。

## 类和函数从设计时考虑通用性

设计公共接口时，先想这个类或函数换一个项目或模型后还能否使用。让核心逻辑依赖必要的数据或行为约定，把会随调用方变化的内容通过普通参数、配置或现有接口传入。比如多个模型都要筛选候选项，可以让筛选函数接收候选项、分数和阈值，由各模型提供这些输入。

保持接口紧凑。参数和抽象层应服务于明确的职责或合理预期的复用点。项目或模型专属的逻辑留在所属边界内。

## 明确状态归属，保持代码清爽

优先使用局部变量。需要跨方法维护的状态由负责它的对象持有。跨组件共享的数据通过明确的接口传递，让读者能看出谁拥有状态、谁会修改它。避免为了少传参数而创建可变全局变量，以及只为一次调用而提升到模块级的变量。确实属于整个模块的稳定常量可以放在模块级。

选能表达含义的名称，保持同层代码的抽象程度和排版一致。完成后顺着调用处读一遍，确认主流程易懂、提取的函数各有职责、可复用的代码能脱离当前项目或模型运行，以及每份状态都有明确的归属。
